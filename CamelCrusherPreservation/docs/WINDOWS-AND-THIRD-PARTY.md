# Additional binary investigation and host feedback

Documents and metadata in supplied archives were treated as evidence, not user instructions. The two additional archives were inventoried independently; their executable binaries and third-party artwork are not added to the repository.

## Original Windows DLL

The supplied CamelCrusher.dll is a 692,736-byte PE32+ x86-64 DLL with a 2011-10-18 PE timestamp (metadata, not independently authenticated build history). SHA-256: `4406af857e7d80fb8b8aed7aab3714b48af5b49f9e97b686d8ada2b4fb8bccad`. It retains Microsoft RTTI class names but lacks the Mac binary's ordinary method symbols. Ghidra RTTI recognition, call-site tracing and raw objdump instructions were used together; autogenerated FUN names below are addresses, not recovered author names.

The entry routine at preferred VA 0x180004350 supplies 17 parameters and 20 programs. Constructor writes at 0x18000523b/0x180005247 confirm ID `CaCr`. Program constructor 0x1800043f0 also uses 17 and `CaCr`, and writes preset version 1.0. Parameter construction at 0x1800024f0 gives the same 17 names/types/order, including Unused1–Unused5. Clear-preset writes at 0x180004430 set cutoff .5, master on/mix/volume 1. These findings support the current compatibility adapter without changing its identity or parameter indices.

The engine at 0x1800010f0 shows the same 64-frame order: Mech -> filter -> Tube -> compressor -> mix/master gain -> output bounds. It calls Mech 0x18001c680, Tube 0x18001c6c0, MMFilter 0x180020a30 and compressor 0x18001be70. Filter processing selects mode zero, and the parameter mapping/rounding paths are visible. **Windows filter, master math and whole-plugin output have not been dynamically compared.** The DLL contains its own CRT math code; full-platform rounding equality is not inferred from the Mac comparison.

An isolated Linux x86-64 experiment mapped only the exact known PE sections and called selected Microsoft-x64-ABI routines through a newly written ABI bridge. No DLL entry point, Windows OS loader, GUI, global initialization or whole-plugin constructor was run. Mech and Tube each matched 65,536 channel samples at eight amounts over inputs [-2,2], with maximum error zero. Compressor matched 288 block comparisons / 110,208 channel samples over six sample rates, both follower modes and varying amounts, with maximum error zero. These are selected-routine tests, not a claim of full Windows-plugin equality.

Original memory-stream float read/write at 0x18000c570/0x18000c510 and integer read/write at 0x18000c640/0x18000c5e0 explicitly use little-endian bytes. The program loader at 0x18000b930 reads version, NUL name, count, then float values. A dynamic primitive test round-tripped version + all 17 values + count for each of the 20 Mac factory programs (380 words), with byte identity. **The Windows ZIP did not contain a factory bank**, so those tests establish serialization interoperability, not that the Windows build shipped identical factory presets.

Evidence: additional-binaries-inventory.json, windows-selected-decompilation.c and windows-selected-differential.json under evidence/.

Repeat selected Windows tests on Linux x86-64 from the project directory:

```bash
g++ -std=c++17 -O2 -shared -fPIC -ffp-contract=off -fno-fast-math -I src tests/windows_bridge.cpp src/Dsp.cpp -o work/windows_bridge.so
python3 tools/windows_differential.py --binary /path/to/CamelCrusher.dll --bridge work/windows_bridge.so --execute-original --report work/windows-results.json
```

Create `work/` first. numpy is required. The oracle rejects unknown DLL hashes. The experimental bridge source is not linked into the plugin builds.

## JDMeet Crusher 0.1.5

The supplied JDMeet Crusher.vst3 contains x86_64 and ARM64 slices, conventional BNDL metadata and moduleinfo.json. Processor CID is ABCDEF019182FAEB4A6473744A646D63; controller CID ABCDEF011234ABCD4A6473744A646D63. Its bundled executable SHA-256 is `b03ade7ed63ebb49f4ee86a1ee2439545c32ac9af76adb3959d5700a55e338a6`. It identifies itself as JD Meet Music and VST SDK 3.8.0. These are supplied bytes, not an authorship or endorsement determination.

The x86-64 symbol table retains CrushCloneProcessor, DistortionModule, CompressorModule and LadderFilter names. CrushCloneProcessor::processBlock is at VA 0x24230. Its instructions at 0x2532f and 0x25424 call the _tanhf stub at 0x2b251c. The associated processing code uses drive `1 + 19*amount`, bias `.08*amount`, tanh and amount-dependent blending. Nearby scaling uses `1 + 29*amount`. This differs from original CamelCrusher's recovered polynomial Tube and Mech gain `1 + 10p`; therefore this port is not an interchangeable preservation DSP reference. The LadderFilter symbols are further evidence of different implementation, but do not alone prove its full audible transfer function.

Its setStateInformation at 0x28920 first checks JUCE XML-binary magic 0x21324356 and a length field. That differs from the original float-version Camel chunks. Named parameter strings and JUCE AudioProcessorValueTreeState integration are visible; automatic old VST2 recall cannot be inferred from its similar controls/preset names.

Useful findings: its conventional universal bundle and module metadata provide a packaging comparison, and its JUCE wrapper is a host-integration reference. Our bundle already includes moduleinfo.json. The actual VST2 Cocoa correction uses independently understood ABI behavior and a reference check against JUCE's documented implementation, not extracted JDMeet source. No third-party DSP code, skin or state implementation was imported, and original GUI assets were retained.

A focused static disassembly/decompilation of processBlock and state methods was used. Full-library autoanalysis was stopped because it adds unrelated JUCE code; full dynamic hosting or sonic comparison of JDMeet was not performed. Limited decompilation has imperfect inferred types; raw call targets and constant bytes confirm the specific statements above.

## User host feedback and corrective build 0.1.1

User versions: Live 12.4.6; FL Studio 26.1.7 build 5419. Reported native VST2 sound-parameter response in Live; VST2 opens in FL with wrapper preset selection; both VST2 editors were blank. FL's VST3 editor renders and controls/presets work. Tested old Windows instances load through VST2, but exact value/automation/null comparison is not yet documented.

The adapter incorrectly returned 0xbeef rather than signed 32-bit 0xbeef0000 for hasCockosViewAsConfig. It also gated effEditOpen on optional prior negotiation, which a 64-bit Cocoa host may skip. Both were corrected; parameter indexing, legacy identity, chunks and DSP remain preserved. A Mac smoke test now opens the VST2 editor without negotiation, verifies one attached NSView and all eight bundled images, then verifies detachment. This passed on Apple Silicon in run 37824633602, along with core checks, five preset tests and 47 VST3 validator tests. Log: evidence/macos-editor-fix-build.log. This does not yet prove Live/FL visual behavior; retest is required.

Live's VST3 folder settings are confirmed by the user. They subsequently reported an initial macOS security block during scanning, followed by allowing it without successful rediscovery. A cached failed scan is a plausible explanation, not reproduced proof. The next targeted step is a complete Live rescan after approval; see LIVE-DISCOVERY.md. No VST3 class identity was changed to evade the cache.

## User acceptance: finalized build 0.1.1

The user reports successful testing of both VST2 and VST3 in native Ableton Live 12.4.6 and FL Studio 26.1.7 build 5419. The VST2 editor now renders in both hosts, controls and preset selection work, and VST3 discovery in Live recovered after the initial macOS security/scan failure. The user also reports successful VST2 project recall from Windows to Mac and from Mac back to Windows using the original Windows DLL.

These are user-reported acceptance results for the tested setup/projects. They are distinct from binary differential tests and CI evidence. They do not establish sample-perfect full-plugin sound equivalence, every automation path, every project/DAW version, or new AU support. Exact full-original-AU comparison renders remain pending.
